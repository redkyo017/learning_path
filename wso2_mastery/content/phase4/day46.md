# Day 46 — Distributed Tracing: ActivityId Correlation

## Why This Matters

In production, a single inbound request to WSO2 API Gateway touches all four services — CP (Control Plane), GW (Gateway), IS (Identity Server), and TM (Throttle Manager). When a request fails, you're staring at four separate log streams:
- CloudWatch Logs: `apigateway-logs`, `identity-logs`, `controlplane-logs`, `throttle-logs`
- Each has thousands of lines per minute
- Manual grep and timestamp matching across four groups: 30 minutes of detective work

**The `activityId` is the thread that ties them together.** It's a UUID generated by the Gateway on every inbound request, stamped into every log line across all four services, and propagated via HTTP headers. With it, a single CloudWatch Insights query across all four log groups gives you the exact sequence of events for one request.

## Core Concepts

### activityId Lifecycle

1. **Generation**: Gateway's `ActivityIDHandler` generates a UUID on inbound request (before any other request processing)
2. **MDC Stamping**: UUID is placed into the thread-local Mapped Diagnostic Context (MDC)
3. **Log Pattern**: Log4j2 configuration includes `%X{activityId}` in the PatternLayout, so every log line in that thread includes `[activityId:xxx]`
4. **Propagation**: When Gateway calls out to Identity Server, Control Plane, or Throttle Manager, it includes the activityId in the `X-Activity-Id` HTTP header
5. **Reception**: Each downstream service receives the header, reads it from MDC, and stamps it into its own local logs
6. **Result**: All four services log the same UUID for the same inbound request

### Log Line Format

```
[2026-09-01 10:01:23,456] INFO {org.wso2.carbon.apimgt.gateway.handlers.security.APIKeyValidationHandler} - [activityId:3f7e8a1b-c221-4d9a-bb35-98f7c042ef0a] JWT validated for /petstore/v1
```

Breaking this down:
- `[2026-09-01 10:01:23,456]` — timestamp (server local time, not UTC)
- `INFO` — log level
- `{org.wso2...APIKeyValidationHandler}` — fully qualified logger class name
- `[activityId:3f7e8a1b-c221-4d9a-bb35-98f7c042ef0a]` — the correlation ID
- `JWT validated for /petstore/v1` — the event message

### Service Identification

You infer the service from the logger class prefix:
- `org.wso2.carbon.apimgt.gateway.*` → **GW** (API Gateway)
- `org.wso2.carbon.identity.*` → **IS** (Identity Server)
- `org.wso2.carbon.throttle.*` → **TM** (Throttle Manager)
- Default → **CP** (Control Plane)

### CloudWatch Insights Cross-Log-Group Query

To query all four logs for a single activityId:
```
fields @logStream, @message 
| filter @message like "3f7e8a1b" 
| sort @timestamp
```

This query:
1. Fetches all log lines containing the UUID from all four log groups
2. Sorts by timestamp
3. Shows you the complete event chain for one request

### Parallel Correlation Mechanisms

WSO2 APIM 4.x maintains **two separate correlation logs** to be aware of:

1. **`wso2carbon.log`** — Event log with activityId stamping
   - Contains every request, error, and state change
   - Includes `[activityId:xxx]` markers for tracing
   - Use this for debugging and incident response

2. **`correlation.log`** — Performance/analytics log (CSV format)
   - Fields: `timestamp|apiContext|apiResourcePath|elapsedTime|applicationName`
   - **No activityId** — designed for analytics dashboards, not tracing
   - Use this for SLA tracking and performance metrics

**Common mistake:** Searching for activityId in correlation.log and finding nothing.

## WSO2 Source: How It Works

### Finding ActivityIDHandler

The `ActivityIDHandler` is the component that creates the UUID and stamps it into MDC:

```bash
find /Users/hunghan/Downloads/wso2am-universal-gw-4.7.0 -name "ActivityIDHandler.java"
grep -n "activityId\|MDC.put\|UUID" <path>
```

Key lines you'll find:
- `MDC.put("activityId", uuid)` — stamps the UUID into thread-local storage
- This runs **before** other request handlers, so all downstream log lines include it

### Finding the Log4j2 Pattern

The `%X{activityId}` token in log4j2.properties tells log4j2 to extract the activityId from MDC and include it in each log line:

```bash
find /Users/hunghan/Downloads/wso2am-universal-gw-4.7.0 -name "log4j2.properties"
grep "%X{activityId}\|appenders.console" <path>
```

Example line from log4j2.properties:
```properties
appender.console.layout.pattern = [%d{ISO8601}] %-5p {%c} - %X{activityId} %m%n
```

The `%X{activityId}` pulls from MDC; if the key doesn't exist, it's empty (no error).

### Header Propagation: X-Activity-Id

When Gateway calls IS, CP, or TM, it passes the activityId via HTTP header:

```bash
grep -rn "X-Activity-Id\|activityId.*header" \
  /Users/hunghan/Downloads/wso2am-universal-gw-4.7.0 --include="*.java"
```

The downstream service receives this header, puts it into MDC, and all its log lines automatically include it.

## Exercises

### Exercise 1: Find ActivityIDHandler
**Question:** In the GW source, which class creates the `activityId` and puts it into MDC? When does it run relative to other request handlers?

**Hint:** Search for `MDC.put` and `activityId` together in the GW source. Think about the order of handler execution — which phase runs before security checks?

**Solution sketch:**
- Class: `org.wso2.carbon.apimgt.gateway.handlers.common.ActivityIDHandler`
- It calls `MDC.put("activityId", UUID.randomUUID().toString())`
- It runs early in the request pipeline, before `APIKeyValidationHandler` and other security handlers, ensuring all downstream handlers see the same activityId in MDC

### Exercise 2: HTTP Header Propagation
**Question:** The GW passes `activityId` to IS via which HTTP header? What does IS do when it receives this header?

**Hint:** Search the GW source for outbound HTTP calls to IS (introspection endpoints). Look for custom HTTP headers being added to the request.

**Solution sketch:**
- Header name: `X-Activity-Id`
- The IS reads this header from the incoming request
- It extracts the activityId value and calls `MDC.put("activityId", headerValue)`
- Result: IS's own log lines show the same activityId as GW, enabling correlation

### Exercise 3: Expected Log Volume
**Question:** A request goes through GW → IS (JWT introspection) → CP (subscription check) → TM (throttle) → backend. How many log lines would you expect to see with the same `activityId` if each service logs on entry and exit?

**Hint:** Count the services and assume two log lines per service. Don't forget that some phases may have multiple internal steps.

**Solution sketch:**
- Minimum: **8 lines** (GW entry, IS entry/exit, CP entry/exit, TM entry/exit, GW exit)
- At DEBUG level: **12+ lines** (additional entry/exit logs for internal functions)
- With timeout retries or subscription checks: 15+ lines
- Rule of thumb: each service boundary crossing logs at least 2 lines (outbound call + callback)

## Key Takeaways

1. **activityId = incident investigation superpower** — one UUID to rule them all
2. **MDC is the plumbing** — log4j2 extracts `%X{activityId}` automatically; just call `MDC.put()` early
3. **Correlation.log ≠ debugging** — use wso2carbon.log for tracing; correlation.log is for analytics
4. **Cross-log-group queries** — CloudWatch Insights on `@message like "activityId-value"` takes 30 minutes into 2 minutes
5. **Every outbound call propagates the header** — X-Activity-Id must be added to HTTP requests to IS, CP, TM

## Anti-Patterns to Avoid

1. **Manual grep across four log groups** — don't do this; use the Day 47 parser or CloudWatch Insights
2. **Confusing correlation.log with wso2carbon.log** — correlation.log is CSV with no activityId; wso2carbon.log has the debug info
3. **Enabling debug logging without setting it in log4j2.properties** — activityId appears even at INFO level, but deeper detail requires `log4j2.logger.APIKeyValidationHandler.level=DEBUG`
4. **Assuming activityId is globally unique forever** — it's unique per request; same activityId appearing again = timeout/retry or new request with collision (rare)
5. **Forgetting to add X-Activity-Id to custom outbound calls** — if you add your own micro-service, propagate the header or trace correlation breaks
