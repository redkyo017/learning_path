# Day 34 — Subscription Management: The Access Control Unit

## Why This Matters

The triple **(Application, API, Subscription Tier)** is the fundamental access control unit in WSO2. Every token issued by the Identity Server carries an `applicationname` claim; the Gateway looks up the subscription using that claim. A missing subscription → **403 Forbidden**, even for a valid JWT. Understanding this boundary is critical: if your JWT is valid but your subscription is inactive, you cannot access the API. This day teaches you how WSO2 separates identity (authentication via IS) from authorization (subscription validation via GW).

## Core Concepts

### The Application Model

An **Application** is a consumer app registered with the CP. Every application has a unique identity tuple:

```go
type Application struct {
    ID             string    // Unique identifier (UUID-like)
    Name           string    // Human-readable name (e.g., "PetApp")
    ConsumerKey    string    // OAuth client ID (what the GW uses to look up the subscription)
    ConsumerSecret string    // OAuth client secret (never re-exposed after creation)
    Owner          string    // Developer who registered the app
    CallbackURL    string    // OAuth callback endpoint
    CreatedAt      time.Time
}
```

**Key insight:** The `ConsumerKey` is generated by the CP (not the developer) and is what the Identity Server uses to identify the application when issuing tokens. The JWT carries an `applicationname` claim; the GW translates this name to a `ConsumerKey` via a local lookup.

### The Subscription Model

A **Subscription** is a mapping between an Application and an API, along with a tier (quota level).

```go
type Subscription struct {
    ID        string             // Unique ID
    AppID     string             // Reference to Application
    APIID     string             // Reference to API
    Tier      string             // Subscription tier (e.g., "Gold", "Bronze")
    Status    SubscriptionStatus // UNBLOCKED (active) or BLOCKED (admin-disabled)
    CreatedAt time.Time
}

type SubscriptionStatus string
const (
    SubUnblocked SubscriptionStatus = "UNBLOCKED"
    SubBlocked   SubscriptionStatus = "BLOCKED"
)
```

**Key insight:** Subscription status can be UNBLOCKED (active) or BLOCKED (admin-disabled). If a subscription is BLOCKED, the GW returns 403 regardless of the JWT validity.

### How Access Control Works

1. **Developer registers an app** → CP generates ConsumerKey/ConsumerSecret
2. **Developer subscribes the app to an API** → CP creates a Subscription record with tier and status UNBLOCKED
3. **Developer calls IS to get a token** → IS issues JWT with `applicationname` = app name, `applicationtier` = tier
4. **Developer calls GW with JWT** → GW:
   - Validates JWT signature (via IS public key)
   - Extracts `applicationname` from JWT
   - Looks up app by name → finds ConsumerKey
   - Looks up subscription by ConsumerKey + API context
   - Checks subscription status (UNBLOCKED?) and tier (matches request tier?)
   - If all checks pass → route to backend; if any fails → 403

### Two Lookup Patterns in the Data Store

The subscription store uses two separate indexes:

1. **`apps map[string]*Application`** (indexed by ID):
   - Used when registering/retrieving applications by ID
   - Example: `POST /applications` → returns app with ID
   - Lookup pattern: "Give me app #abc123"

2. **`byKey map[string]*Application`** (indexed by ConsumerKey):
   - Used when validating subscriptions at request time
   - Example: GW receives JWT with `applicationname`; translates to ConsumerKey; looks up app
   - Lookup pattern: "Give me app with ConsumerKey 'xyz789'" → O(1) instead of O(n) scan

Using two maps provides O(1) for both patterns. A single map would force O(n) scans during validation, which would be catastrophic under load.

### The AM_SUBSCRIPTION Table (from WSO2 Source)

In production WSO2, the `AM_SUBSCRIPTION` table stores subscriptions:

```
Columns:
  SUBSCRIPTION_ID (primary key)
  APPLICATION_ID  (foreign key → AM_APPLICATION)
  API_ID          (foreign key → AM_API)
  TIER_ID         (foreign key → AM_POLICY_SUBSCRIPTION)
  SUBSCRIPTION_STATUS (UNBLOCKED | BLOCKED)
  CREATED_BY      (developer username)
  CREATED_TIME    (timestamp)
  UPDATED_TIME    (timestamp)
```

The **`SUBSCRIPTION_STATUS`** column is the gate: if it's BLOCKED, the GW rejects the request.

### Soft Deletes vs. Hard Deletes

WSO2 never hard-deletes subscription records. Instead, it marks them as BLOCKED. This allows:
- Audit trails: You can see all subscriptions (active and inactive)
- Recovery: An admin can unblock a subscription later
- Rate limit tracking: The GW can still enforce rate limits on blocked subscriptions (edge case)

When a developer "unsubscribes" from an API, the CP sets `SUBSCRIPTION_STATUS = BLOCKED`, not `DELETE FROM AM_SUBSCRIPTION`.

```
Key columns:

  - UPDATED_BY, UPDATED_TIME: Audit fields
```

### Exercise 2: Publisher vs. Consumer View
**Q:** What is the difference between `getSubscriptionsByAPI()` and `getSubscriptionsByOwner()`?

**Hint:** One query is used by the publisher (API owner) to see who subscribed; the other is used by the consumer (app owner) to see what they subscribed to. Both query `AM_SUBSCRIPTION`, but with different filters.

**Solution sketch:**
```
getSubscriptionsByAPI(apiId):
  SELECT sub.* FROM AM_SUBSCRIPTION sub
  WHERE sub.API_ID = ?
  
  Returns: All subscriptions (all apps) for this API
  Used by: API owner (publisher) to monitor who subscribed
  Context: "Show me all apps using my API"

getSubscriptionsByOwner(ownerUsername):
  SELECT sub.* FROM AM_SUBSCRIPTION sub
  INNER JOIN AM_APPLICATION app ON sub.APPLICATION_ID = app.APPLICATION_ID
  WHERE app.CREATED_BY = ?
  
  Returns: All subscriptions owned by this developer
  Used by: Developer (consumer) to see their app's subscriptions
  Context: "Show me all APIs my app is subscribed to"

Key difference:
  - getSubscriptionsByAPI: Publisher view (API-centric)
  - getSubscriptionsByOwner: Consumer view (App-centric)
```

### Exercise 3: Tier Information in the JWT
**Q:** How does the Gateway know an application's subscription tier at request time? Does it call the CP every time?

**Hint:** The JWT carries a tier claim. Search WSO2 source for `applicationtier` or look at the IS token response.

**Solution sketch:**
```
The GW does NOT call the CP on every request.

Instead, the IS embeds the tier claim in the JWT at token issuance:

  JWT payload:
  {
    "sub": "user@app.com",
    "aud": "app_key",
    "iat": 1234567890,
    "exp": 1234571490,
    "iss": "https://identity-server:9443",
    "http://wso2.org/claims/applicationname": "PetApp",
    "http://wso2.org/claims/applicationtier": "Gold"
  }

The GW reads "Gold" from the JWT without calling the CP.

Why this design?
  - Performance: No network call needed for every request
  - Consistency: Tier information is immutable for the lifetime of the token
  - Failure resilience: If the CP is down, the GW can still validate active tokens

Trade-off:
  - If an admin blocks a subscription or downgrades a tier, the GW won't know until the token expires
  - Solution: The CP emits a SUBSCRIPTION_UPDATED event; the GW invalidates its local cache for that app+API pair
```

## Anti-Patterns to Avoid

1. **Calling the CP on every request to validate the subscription** — The GW must cache subscription data locally and only refetch on cache miss. Calling the CP 1000× per second will overwhelm it.

2. **Confusing the application `ConsumerKey` with the JWT `sub` claim** — The `ConsumerKey` is generated by the CP and is internal. The JWT `sub` claim is the end-user identifier (e.g., `user@app.com`). The GW uses `applicationname` (not `sub`) to look up the subscription.

3. **Blocking a subscription at the DB level but not propagating the change to the GW event stream** — If you set `SUBSCRIPTION_STATUS = BLOCKED` in the DB but don't emit a `SUBSCRIPTION_UPDATED` event, the GW keeps the old subscription data in memory and continues to allow requests. Always emit events.

4. **Using a linear scan to find subscriptions by ConsumerKey** — If the store doesn't index by ConsumerKey, validation becomes O(n) and the system fails under load. Always use a secondary index.

5. **Exposing the `ConsumerSecret` in GET responses** — The `ConsumerSecret` is sensitive. Expose it only at app creation time. On all subsequent GETs, return `"consumerSecret": "***"` or omit it.
