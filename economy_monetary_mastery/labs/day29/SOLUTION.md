# Lab 29 — Solution notes

## _log
Build `{"ts": now_iso, **record}` and append `json.dumps(rec) + "\n"` to the log file in append mode. One JSON object per line (JSON Lines) means a crash mid-run never corrupts earlier lines, and `jq` or pandas can read the file. Use a timezone-aware UTC timestamp. Common mistake: writing a JSON array (needs rewriting the whole file) or opening in `"w"` mode so every step erases the history. `test_log_lines_are_json` expects exactly two lines after two steps, each with all required keys.

## _flatten
Read the position; if it is positive, submit a market `sell` for exactly that quantity; if flat, do nothing (`FakeBroker` rejects zero-quantity orders). Common mistake: submitting an order when flat, which raises, or selling a hard-coded size. `test_daily_loss_kill_switch_flattens_and_stays_off` asserts the position is 0 and that only two orders exist in total (the entry and one flatten), so a second flatten on the next step is caught.

## step
Order matters. (1) Before fetching any data: `killed` or the kill file present -> `_kill`, which latches `killed=True` first, then flattens, logs (price and equity are best-effort, `None` if the feed is down) and returns `{"action": "killed", "side": None, "qty": 0.0}`; if the sell raises, the error is logged and re-raised, `killed` stays True and the next step retries the flatten. Then fetch price and equity once; (2) `equity < day_start_equity*(1-max_daily_loss)` -> same path; (3) a non-finite weight (NaN/inf) is a hold; otherwise `w = min(max(strategy(history), 0), 1)`, `target_qty = min(w*equity, max_position_notional)/price`, `delta = target_qty - position`; if `abs(delta)*price < min_order_notional` it is a hold, otherwise `qty = min(abs(delta), max_order_notional/price)` and submit `buy` for positive delta, `sell` for negative; (4) log every step. Kill checks come before the strategy so a bad signal can never override a safety rule, and `killed` is a latch, never reset by the loop.
Common mistakes: clipping the weight after computing the target (the 1.7 weight test expects 100 units, not 170); applying the order cap to the target instead of the delta (the order-cap test needs two steps to reach 20 units); forgetting that a latched kill must keep returning `killed` without new orders (`len(b.orders) == 2`); checking the kill file after `get_price` (a dead feed would then block the kill; `test_safety.py` covers it); latching `killed` after the flatten (a failed sell would leave the bot live); not logging holds (the log test counts two lines for two steps, one of which is a hold-or-order, so every step must log).

## What the output means
`main()` replays the last 365 BTC/USDT daily closes (2025-10-01 to 2026-09-30) through `FakeBroker` with a long/flat 50-day momentum rule and a 15% daily-loss limit. It makes 23 orders and 342 holds, ends near 9,874 from 10,000, and avoids most of a 30% buy-and-hold loss (7,051), mostly by being flat while BTC trended down. The kill switch never fires: the worst single-day equity change while the bot was long is about -7.3% of the previous day's equity, short of the 15% limit (the day starts at the previous close because `replay` calls `new_day()` before the new price arrives). The trade count is the lesson: every order is a fill the fake broker gave at the close with no fee, no slippage and no partial fill, so the 23 orders (about 11 to 12 round trips) look free here and would not be live. The log has one line per decision, which is what lets you reconcile after the fact.
