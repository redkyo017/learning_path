# Day 2 solution

Two independent faults. Fault B hides fault A: fix B first, and the pings return but the
download still hangs.

## Fault B: a more specific route to a dead next hop

Symptom: pings to 10.2.2.10 fail, though the default route is untouched.

```bash
ip -n h1 route get 10.2.2.10     # 10.2.2.10 via 10.2.1.99 dev eth0 src 10.2.1.10
ip -n h1 route                   # 10.2.2.0/25 via 10.2.1.99 is listed alongside the default route and wins by longest prefix
ip -n h1 neigh                   # 10.2.1.99 dev eth0  FAILED
```

Evidence chain: the lookup is longest-prefix-match, and 10.2.2.0/25 (a /25 covers
10.2.2.0 to 10.2.2.127, so it contains .10) is longer than the /0 default. The next hop
10.2.1.99 is on-link, so h1 sends an ARP request for it. Nobody answers, the neighbour
entry goes INCOMPLETE and then FAILED, and the packet is never sent. In a capture on
h1 `eth0` you see only repeated `ARP, Request who-has 10.2.1.99`.

Fix:

```bash
ip -n h1 route del 10.2.2.0/25
```

## Fault A: the black hole for full-size packets

After fix B, `verify.sh` shows both pings passing and the 200 KB transfer failing. Small
packets cross; large ones do not. That pattern points at MTU.

```bash
ip netns exec h1 ping -M do -c2 -s 1472 10.2.2.10   # no reply, and no "Frag needed" either
ip netns exec h1 ping -M do -c2 -s 1372 10.2.2.10   # replies
```

h2 keeps what it learns from ICMP 3/4 for 10 minutes (`ip -n h2 route get 10.2.1.10`
shows `cache expires ... mtu 1400` once learned), so a transfer that succeeded earlier can
hide the fault. `break.sh` flushes these caches; if you re-test after fixing, also run
`ip -n h1 route flush cache; ip -n h2 route flush cache` so you test the path, not the cache.

A healthy path answers the first command with `From 10.2.1.1 ... Frag needed and DF set
(mtu = 1400)`. Here there is silence.

Find where the packet dies, with two captures in r2 (run them before `curl`):

```bash
ip netns exec r2 tcpdump -ni eth2 -c8 'tcp port 8080'    # h2 side
ip netns exec r2 tcpdump -ni eth1 -c8 'tcp port 8080 or icmp'   # r1 side
ip netns exec h1 curl -s -o /dev/null --max-time 3 http://10.2.2.10:8080/big.bin
```

On `eth2` you see the handshake and the request arrive, then h2's data segments of 1448
bytes (1500-byte packets, since both TCP ends negotiated MSS 1460), sent again and again.
On `eth1` the handshake and request cross, but the 1500-byte segments never leave toward
r1. No `ICMP ... unreachable - need to frag (mtu 1400)` goes out of `eth2` back to h2.
r2 cannot forward 1500 bytes into a 1400 link, so it must drop the packet and, because DF
is set, send ICMP type 3 code 4 to the source. That error is missing.

```bash
ip netns exec r1 nft list ruleset
ip netns exec r2 nft list ruleset
```

Both show `table inet lab` with an output-hook rule `icmp type destination-unreachable
icmp code frag-needed drop`. The ICMP error is generated by the router itself, so it
traverses the output hook, and the rule discards it.

Explanation: this is a path MTU discovery black hole (RFC 1191). TCP sets DF and relies on
the router that cannot forward to say so with ICMP 3/4 carrying the next-hop MTU. With the
error filtered, h2 never lowers its segment size, retransmits the same 1500-byte segments,
and the transfer stalls. Small packets (handshake, pings, health checks) fit in 1400, which
is why everything else looks healthy. The rule is on r1 as well because r1 originates the
error for large packets that h1 sends toward h2.

Fix:

```bash
ip netns exec r1 nft delete table inet lab
ip netns exec r2 nft delete table inet lab
```

## Confirm

```bash
ip netns exec h1 ping -M do -c1 -s 1472 10.2.2.10
# From 10.2.1.1 icmp_seq=1 Frag needed and DF set (mtu = 1400)
bash labs/day02/verify.sh        # PASS: day 02 is healthy.
```

h1 now caches the discovered MTU for 10.2.2.10 (`ip -n h1 route get 10.2.2.10` shows
`mtu 1400` once an error has arrived), and TCP uses it.

## Journal sentence

"A black-holed PMTUD on AWS is a filtered ICMP 3/4 on the wire: allow type 3 code 4 in the
security group or NACL, or clamp the MSS at the tunnel."
