# Day 17 Lab — SOLUTION

## Answers to `fido2_registration.http` questions

### Step 1 (Registration Start)

**What is the purpose of the `challenge`?**
The `challenge` is a fresh cryptographic nonce generated by IS 7.3 per ceremony. The authenticator
embeds this challenge in the `clientDataJSON` and signs it. IS 7.3 verifies the signature includes
the exact challenge it issued. This prevents **replay attacks**: an attacker who captures a previous
registration or assertion response cannot replay it — the challenge is consumed once and expires.
IS 7.3 stores the challenge in the server-side session and invalidates it after the `finish` call
or after the timeout.

**Why is `userVerification: required` specified?**
This policy tells the authenticator it MUST perform user verification (PIN or biometric) before
signing. If the authenticator cannot verify the user (e.g., no PIN set), the ceremony fails with
`NotAllowedError`. IS 7.3 later checks the UV (User Verified) flag in `authenticatorData` — if it
is not set but the policy is `required`, IS 7.3 rejects the assertion. This enforces PSD2 SCA:
the ceremony proves both possession (the key) and knowledge/inherence (PIN/biometric).

**What is `excludeCredentials` used for?**
IS 7.3 populates `excludeCredentials` with the credential IDs the user already has registered from
this authenticator. If the authenticator detects that it already has a credential in this list,
it throws `InvalidStateError` — preventing a duplicate registration from the same device. This
ensures each authenticator-RP pair has exactly one credential per user.

### Step 2 (Registration Finish)

**What does `attestationObject` contain?**
`attestationObject` is CBOR-encoded and contains three fields: `fmt` (attestation statement format,
e.g., "packed"), `attStmt` (the attestation statement — the authenticator's signature over the
registration data, made with the authenticator's attestation key, not the credential key), and
`authData` (authenticatorData — rpIdHash, flags including UP and UV, signCount=0, and the new
credential public key in COSE format). IS 7.3 extracts the public key from `authData` and verifies
the attestation signature against the authenticator model's certificate chain (for `direct` attestation).

**What does `clientDataJSON` contain, and why does IS 7.3 check its `origin` field?**
`clientDataJSON` contains `type` ("webauthn.create"), `challenge` (the nonce), `origin` (the web
origin that called `navigator.credentials.create()`), and `crossOrigin`. IS 7.3 checks `origin`
against its configured RP origins list to prevent a phishing site from registering credentials under
the bank's RP ID. If a user was tricked into visiting `evil.example.com` and that page called the
FIDO2 API, the `origin` in `clientDataJSON` would be `https://evil.example.com`, which IS 7.3 would
reject because it does not match `https://banking.example.com`.

**What does IS 7.3 store after this request?**
IS 7.3 stores:
- `credentialId` — unique identifier for this credential (sent in `allowCredentials` at future assertions)
- Public key — COSE-encoded (EC P-256 or RSA); used to verify all future assertion signatures
- `signCount` — initialised to 0; incremented on each assertion; used to detect cloned authenticators
- `userHandle` — links the credential to the IS 7.3 user account
- `rpId` — scopes the credential to `banking.example.com`
The private key is NOT stored — it never leaves the authenticator.

### Step 3 (Assertion Start)

**Why does IS 7.3 include `allowCredentials`?**
`allowCredentials` is the list of credential IDs IS 7.3 has stored for this user on this RP. The
authenticator uses this list to locate the correct key — it tries each credential ID and uses the one
it has stored. Without `allowCredentials`, a non-resident-key authenticator would not know which
credential to use for this RP. Resident keys (passkeys) do not require this hint because the
authenticator can discover its own credentials for the RP.

**What changes for a resident key (passkey) flow?**
Two changes: (1) The assertion start request omits `username` (or sends an empty string). IS 7.3
cannot look up a user's credentials because it does not know who is logging in. (2) IS 7.3 returns
`allowCredentials: []` (empty). The authenticator enumerates its own resident credentials for the RP,
presents an account picker to the user, and the user selects which account to authenticate as. The
`userHandle` in the assertion response tells IS 7.3 which user authenticated.

### Step 4 (Assertion Finish)

**What does IS 7.3 verify in `signature`?**
IS 7.3 verifies that the `signature` is a valid ECDSA (or RSA) signature over the concatenation of
`authenticatorData` bytes and `SHA-256(clientDataJSON)`. It uses the stored public key for the
`credentialId` specified in the assertion. A valid signature proves the authenticator that registered
this credential is present and the private key has not been exported.

**What does IS 7.3 check about the `userVerification` flag?**
`authenticatorData` contains a flags byte. Bit 2 is the UV (User Verified) flag. Because the policy
is `userVerification: required`, IS 7.3 checks that UV=1. If the flag is 0 — the authenticator
completed the ceremony without verifying the user — IS 7.3 rejects the assertion. This is the
server-side enforcement that makes `userVerification: required` effective for SCA: the client cannot
bypass it by sending a `discouraged` assertion response.

**Why does IS 7.3 track `signCount`?**
`signCount` is a monotonic counter the authenticator increments on every assertion. IS 7.3 stores the
last `signCount` seen for each credential. If a new assertion has a `signCount` lower than or equal
to the stored value, it indicates the authenticator has been cloned (two devices sharing the same
private key, both incrementing from the same starting point). IS 7.3 can reject the assertion or
flag it for fraud review. Software authenticators (platform authenticators that use the OS keystore)
sometimes return `signCount=0` — IS 7.3 treats 0 as "not tracked."

## Stretch exercise answers

**1. Enabling resident key storage:**
Add `"residentKey": "required"` (and `"requireResidentKey": true` for older authenticator compat)
to `authenticatorSelection` in the registration start request. This signals to the authenticator that
it must store the credential as a discoverable resident credential, indexed by `rpId`. Without this,
the credential may be stored in a way that requires `allowCredentials` to locate it.

**2. Allowing authentication without a username:**
Send `POST /fido2/v2/assertion/start` with an empty body (or `{}` — no `username`). IS 7.3 returns
`allowCredentials: []`. The browser passes an empty `allowCredentials` array to the authenticator,
which searches its own storage for resident credentials for `banking.example.com` and presents an
account picker. The `userHandle` in the assertion response resolves the user identity on the IS 7.3 side.
